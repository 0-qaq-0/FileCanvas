# FileCanvas 从开发体验到日常产品：实施规划

日期：2026-10-16。状态：规划与代码审查完成，产品功能改造待实施。本轮不打包 EXE；下一阶段先交付可运行、可维护、可验证的源码。

## 1. 产品目标和首版范围

产品定义：**先看清文件，再在画布上整理，确认后把结果可靠地应用到本地，并能查看和恢复最近一次操作。**

第一批使用场景默认是 Windows 上的下载文件、学习资料和单个项目素材目录。先把一个具体目录用好，逐步扩展。AI 用于解释与提出位置建议；不配置 AI 时，浏览、拖动、核对、应用、恢复仍完整可用。

“与画布一致”指真实文件/文件夹的名称和目录层级与最终确认的计划一致。卡片的屏幕位置、缩放和展开状态属于软件内的个人视图，保存于项目中；它们不能直接对应资源管理器的图标坐标。

下一源码版建议标为 0.4.0 开发版，完成后再按实测确定可用范围，不能仅靠版本号当作稳定承诺。

| 首个源码版本必须完成                                               | 后续版本再扩展                               |
| ------------------------------------------------------------------ | -------------------------------------------- |
| 所选项目目录内的文件移动、重命名、文件夹新建/移动/重命名与嵌套组合 | 跨磁盘、网络盘、目录联接和云端同步           |
| 整理草案持久化、预览与执行一致、执行结果核验                       | 多目录汇总、定时整理、规则市场               |
| 异常退出后可识别并处理，最近一次磁盘恢复                           | 任意历史操作的一键回放/回滚                  |
| 无 AI 完整使用，AI 建议有依据且手动采用                            | OCR、PDF/Office 正文、图像语义、全电脑知识库 |
| 当前流程和历史版本说明清楚分开                                     | EXE 签名、安装器、自动更新                   |

第一版以本地同卷 NTFS 为首要验收环境。当前硬链接方案依赖文件系统能力，执行前必须检查；不支持的环境应在进入确认前说明。增加其他环境要先做专门验证，不能把“本地路径”一概视为都支持。

## 2. 日常使用闭环

1. **打开目录**：扫描真实文件；说明整理范围、被排除/无法读取的条目和规模限制。演示入口作为可选教程。
2. **查看与整理**：展开文件夹，看内容，拖动或使用“移动到”；可撤销计划。始终显示“尚未应用 · N 项变化”。
3. **检查结果**：同屏比较原结构和目标结构，列出移动、新建、重命名、保留项和阻塞项。未导入/排除的真实文件保留，并在结果中说明，不能让它们悄悄消失于用户的理解中。
4. **确认应用**：冻结用户看到的版本，生成确定的操作计划，重新核对磁盘，展示项目根目录和数量，再执行。
5. **执行与核验**：显示进度，记录每一步，完成后重新扫描并验证路径与内容。全部一致才能显示“已应用并核验”。
6. **继续使用与恢复**：查看结果、在资源管理器中定位、继续整理、恢复最近一次操作。重启先处理未完成任务，再开始新的磁盘操作。

应用过程中如外部程序改变了文件，应停止受影响操作并说明已完成的部分；不得把部分完成当作全部完成。多文件系统操作无法简单保证全批同时生效，产品需要承诺可追踪、可核对和可恢复。

## 3. “确认后实际一致”的实现方案

### 3.1 让预览与执行使用同一份计划

抽出独立的操作计划模块：输入当前草案和真实目录基准，输出唯一计划 ID、项目修订号、操作依赖、预期前后路径、受影响项和不可执行原因。前端预览和主进程执行都使用它。

用户确认后不能把新的画布草案混入旧预览。磁盘或项目版本变化时让旧计划失效，显示差异并重新预览。不能在预览里通过、点确认才告知某种操作不支持。

### 3.2 处理文件夹与子文件的依赖

文件夹整体移动、改名以及其内部文件再分类，不能按列表逐行直接移动。先计算整棵树的最终路径，再安排父子依赖和必要中间路径；遇到循环、同名、大小写名称变更和路径冲突使用专门处理或在预检阻止。

已有文件夹只有在完整掌握受影响子树时才能整体操作。发现未导入条目、外部新文件或读取失败，先让用户看到并决定完整纳入或调整计划；不能丢下未纳入文件却宣称整个文件夹已按画布移动。

### 3.3 修复执行日志和重启恢复

- 日志按操作 ID 保存，包含格式版本、项目修订、执行前后快照、每项意图、检查信息和实际进度。
- 每一步在修改前记录意图，修改后记录结果；日志写入采用临时文件替换并按需要同步落盘，明确进程崩溃与断电的不同保证范围。
- 恢复时以日志结合真实磁盘状态判断，允许重复核对和重复恢复；覆盖本轮发现的链接已建但未记账、路径已恢复但未记账两种状态。
- 对同名外部文件、内容修改、权限变化等情况保留数据并进入恢复处理页，列出路径和下一步，不用短暂提示替代处理入口。
- 磁盘操作和项目保存作为一个完整任务管理：即使文件已移动、项目未保存，重启仍能重建正确项目或引导恢复。

### 3.4 应用完成后做独立核验

对参与整理的文件核对最终路径、类型、数量与内容摘要；确认原路径是否应消失；核对新旧文件夹状态；对未参与项检查未被误动。检测到差异时显示“需要处理”，不宣称完成。

默认保留原有空文件夹，以避免意外删除；预览明确列出“保留的空目录”。若要清理，只提供用户主动选择的“仅清理本次变为空的目录”，重新检查为空并记录恢复信息。最终结果展示必须把保留目录包含在内，不能只画出理想结构。

“恢复整理”只恢复本工具的位置/名称操作。移动后被外部编辑的内容不回滚；检测到修改先说明，再提供可核对的处理方式。

## 4. 易用性改造清单

| 部位       | 要做的改变                                                                                | 用户能得到的结果                   |
| ---------- | ----------------------------------------------------------------------------------------- | ---------------------------------- |
| 主操作     | 固定显示“检查并应用（N）”；点击进入核对；核对页唯一主按钮为“应用到本地文件”               | 清楚知道怎样从草案到真实整理       |
| 当前状态   | 持续展示“尚未应用 / 执行中 / 已应用并核验 / 需要处理”                                     | 不把保存项目误认为已经移动文件     |
| 文件卡片   | 类型图标加扩展名小标签；图片缩略图加载失败显示图片图标；PDF、文档、表格、代码、音视频区分 | 不打开也更容易辨认文件             |
| 文件夹     | 展开箭头只负责展开；“单独查看”“查看内容”给文字提示；新建待应用目录有标记                  | 减少小图标含义混淆                 |
| 文件动作   | 预览用眼睛；用系统应用打开用外部打开图标并有提示；常用动作可见                            | 不靠记忆判断每个按钮               |
| 拖动       | 显示“将放入：目标路径”，目标高亮；无效目标说明原因；保留“移动到”替代拖动                  | 拖到哪里、结果是什么可预见         |
| 待变更项   | 卡片显示“待移动/待改名”；可以只看变化并定位目标                                           | 大目录里仍能找到自己改过的文件     |
| 撤销与恢复 | 工具栏“撤销计划（Ctrl+Z）”；结果区“恢复上次文件移动”                                      | 区分画布修改和真实文件恢复         |
| 出错与冲突 | 持续保留问题列表，提供定位、刷新、调整计划、进入恢复                                      | 不再因提示消失而无从处理           |
| 外部变化   | 增加“刷新并核对”，列出新增/修改/缺失，保留可复用草案                                      | 真正支持文件每天继续变化           |
| 初次使用   | 三步引导：选目录→整理→核对应用；示例为可选入口                                            | 新用户可以直接处理自己的小目录     |
| 视图记忆   | 保存展开状态、面板宽度与滚动/缩放；只把有价值的设置保留                                   | 重启后继续上次整理位置             |
| 键盘与窗口 | 补齐焦点、提示文本、对话框焦点管理；1000×680 与高 DPI 检查                                | 少依赖鼠标精准点击，避免遮挡和溢出 |

沿用现有 Lucide 矢量图标和类型色彩，状态同时使用文字，不只依赖红绿颜色。先统一按钮含义和状态，再细调视觉样式。复杂缩放平移若影响实现范围，可以后置，但不能让待变更项无法定位。

## 5. 维护与更新设计

继续在当前 Git 仓库开发，建议从现有提交建立 `feature/productization` 分支；每个阶段完成对应验收再提交，源码交付时建立版本标签。Git 用于恢复代码，文件移动恢复依靠执行日志；二者用途分别说明。

| 维护事项   | 实施内容                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| 模块边界   | 分开目录读取、操作计划、磁盘执行、恢复、项目存储、AI 与界面；App 的会话/保存/执行流程逐步拆成独立 hooks 或服务 |
| 类型与状态 | 统一任务状态与错误类型；主进程管理文件任务，UI 订阅进度；避免在组件里零散推测恢复结果                          |
| 数据兼容   | 项目、设置、日志各有格式版本；迁移前备份，迁移失败保留原文件；拒绝静默丢弃旧数据                               |
| 保存体验   | 保存状态清楚；合理合并高频布局保存；关闭等待最后一次保存；保存失败可重试                                       |
| 开发数据   | 保持开发版与正式版数据隔离；开发代码不直接迁移用户重要文件                                                     |
| 回归流程   | 固定依赖锁文件；每次变更执行相关单测、类型检查和必要桌面验收；提交前复查 UTF-8                                 |
| 更新记录   | 根 README 指向唯一当前说明，新增 CHANGELOG 与版本验收记录；历史 0.3.0 文档保留并标为历史                       |
| 问题排查   | 提供版本、任务 ID 与可导出的诊断报告；默认去除密钥、文件正文和不必要的私人路径                                 |
| 后续 EXE   | 先手动更新流程和数据兼容，再评估签名与自动更新；未解决未完成任务前不应触发应用升级                             |

不建议为了产品化立刻重写框架。先在现有模块上建立边界，并用有价值的回归验证重构。

## 6. 分阶段实施与验收

以下为开发工作量估计，不是日历承诺；文件夹依赖与故障恢复的结果可能影响工期。每阶段结束交付可查看的源码和证据。

| 阶段                | 主要步骤                                                                               | 必须看到的结果                                                                         | 粗估         |
| ------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------ |
| A：执行安全基础     | 为 R1/R2 建立正确行为回归；统一计划/预检；操作日志版本化；启动恢复页；处理项目保存中断 | 每个文件操作边界中断都能正确识别；不能恢复时明确保留文件；R3/R4 未补齐时必须在预览阻止 | 3–5 个开发日 |
| B：完整结构应用     | 支持同卷文件夹移动/改名、父子组合、大小写改名；冻结确认版本；执行后重扫核验            | 支持范围内真实目录等于确认结构；未参与项未误动；文件摘要一致                           | 3–5 个开发日 |
| C：日常工作流与界面 | 固定应用入口、变更标记、类型图标、拖放反馈、冲突处理、刷新核对、视图保存               | 不依赖 AI，首次使用者也能从自己的小目录完成整理并恢复                                  | 2–4 个开发日 |
| D：可维护源码交付   | 数据迁移与旧项目检查；文档同步；性能和桌面回归；整理源码包和交付清单                   | 新目录解压后按说明安装依赖即可运行，源码包不含私人数据，测试结果明确                   | 1–2 个开发日 |

推荐先做 A+B，然后在一个真实、可备份的小目录试用，记录阻碍，再完成 C+D。整体粗估 9–16 个开发日；先交付 A 的结果后再调整剩余估计。

## 7. 不是演练的验收方式

| 用例               | 验收标准                                                                     |
| ------------------ | ---------------------------------------------------------------------------- |
| 普通文件与嵌套目录 | 移动、重命名、父子混合调整后，真实名称和层级与确认版本一致                   |
| 无 AI              | 未配置密钥/离线时可完成整理、应用和恢复                                      |
| 外部变化           | 在预览之后新增、修改、删除或占用文件，应用前发现并说明；不覆盖新文件         |
| 中途失败/退出      | 执行与撤销各步骤注入失败和进程退出；重启不会误报成功；保留可处理的任务       |
| 项目保存失败       | 文件成功移动但保存项目失败时，重启仍可正确核对、补完或恢复                   |
| 连续两次整理       | 历史保留；恢复入口明确对应哪次；不会让用户误以为可随意回到任意过去状态       |
| 部分导入和排除项   | 未纳入文件和保留空目录有明确去向；不误动、不中途遗失                         |
| 中文和常见边界     | 中文、空格、特殊合法名称、大小写、长路径提示、只读与权限限制均有测试         |
| 规模与显示         | 先测 100/500/1000 项、嵌套展开和常见图片；报告机器配置与耗时，再确定流畅规模 |
| 旧数据升级         | 旧项目能读取或明确迁移；失败保留备份；未完成日志不能被新版本忽略             |

使用验证分三步：自动测试临时目录 → 真实目录的独立副本 → 用户选定且已备份的小目录。第三步完成后再找少量实际使用者记录任务完成率、无法继续的原因和是否愿意复用。通过桌面测试仅证明工程流程，不等于有人需要或愿意付费。

第一份真实使用记录至少包含：原始文件数量、想完成的结构、应用清单、执行结果、恢复结果、操作用时和遇到的问题。不要用演示截图代替这份记录。

## 8. 源码交付内容

- 保持当前 `01_源码`、`02_测试`、`04_构建脚本`、`05_项目文档` 结构，交付 package.json、锁文件与构建配置。
- 包含启动说明、当前功能与限制、操作/恢复指南、数据目录说明、CHANGELOG 和该版本验收报告。
- 包含虚构测试样例、单元测试和桌面测试；本轮审查复现应转成缺陷修复回归。
- 提供源码 ZIP、文件清单、版本与对应 Git 提交、SHA-256；在独立目录按说明安装依赖并验证可运行。
- 不包含 node_modules、历史 EXE、构建输出、个人项目快照、操作日志、AI 密钥或私人文件；源码中的示例必须为虚构内容。
- 同时说明项目当前的许可证状态（目前 package.json 为 UNLICENSED）；对外开源或商业分发前再明确许可和第三方说明。

“交付源码”不要求先制作 EXE。源码可在 Node/Electron 开发环境运行；独立安装包、签名和自动更新是之后的发布阶段。

## 9. 建议下一步

建议按 **A → B → 小目录实用 → C → D** 推进，先交付 0.4.0 源码，再决定 EXE。

若希望选择实施节奏，两个可行选项如下：

| 选项               | 我会依次做什么                                                                              | 得到的结果与取舍                                                             |
| ------------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 完整首版（推荐）   | 修恢复和预检 → 完成文件夹/子项应用 → 用小目录验证 → 改易用性 → 数据兼容、文档和源码交付     | 支持日常整理的主要操作，最符合“最终结构能应用到本地”；工作量较大             |
| 先做普通文件可用版 | 修恢复和预检 → 明确阻止已有文件夹移动/改名 → 完善应用入口和结果核验 → 小目录验证 → 交付源码 | 更早得到可靠的有限功能版；只能搬文件和创建分类目录，完整文件夹整理仍需下一轮 |

图标美化可以穿插，但不能替代恢复与一致性验收。不建议只换图标就把当前开发版称为可放心使用的正式产品。
