# FileCanvas 产品化代码审查

日期：2026-10-16。审查基线：Git `8337911`。范围：当前开发源码、本地文件操作、持久化、预览确认、界面状态、现有测试与文档；本轮没有修改产品功能，没有生成 EXE。

**后续实施状态：** 下文保留审查当时的发现和旧代码行号。0.4.0 源码版已经修复 R1–R4，并补充执行核对、恢复入口、记录归档和刷新核对；当前使用范围与已有验证见 [0.4.0 说明](0.4.0源码版使用与交付说明.md)。此处“尚未修复”等判断只对应上述基线，不代表新版现状。

## 结论

现有开发版已经具备真实普通文件移动、重命名、新建分类目录与最近一次磁盘撤销，并非完全只读的演示程序。但**正常流程测试通过，不等于异常恢复和全部画布操作已经可交付**。当前不宜直接宣称“画布整理后的结构都可以可靠地应用到本地”。

建议保留 Electron + React + TypeScript 现有架构，先修复恢复机制与预览/执行差异，再完善日常工作流和界面，最后交付可重复运行的源码版本。实施顺序见 [产品化实施规划](产品化实施规划_2026-10-16.md)。

## 已确认的代码问题（按优先级）

### R1 · P1：移动中断后，撤销可能误报完成并留下额外目标文件

- 位置：`01_源码/electron/disk-operations.ts:224-228`、`:82-85`、`:95-96`。
- 触发：`fs.link(source, target)` 已完成，但 `linked` 状态尚未保存时进程退出。
- 原因：磁盘已经有两个硬链接，持久日志仍是 `planned`。恢复逻辑直接跳过 `planned`，没有按真实路径和文件身份进行核对。
- 实际复现：子进程在链接成功后立即退出，重新创建 DiskOperations 并调用 undo；undo 返回成功，但 source 和 target 均存在。没有观察到样本文字内容丢失，但磁盘结构与“恢复完成”不一致。
- 修复：为每项操作持久化意图；重启时检查源、目标、内容摘要及文件身份，辨认“未做”“已做但未记账”“已恢复”等状态。恢复必须可重复执行，最后重扫并验证再报告成功。
- 验收：在链接前后、日志保存前后、移除源路径前后分别中断，重启恢复后只有预期路径，内容一致；无法确定的情况明确显示需处理，不能报成功。

### R2 · P1：撤销中断后，已恢复的操作不能被再次正确识别

- 位置：`01_源码/electron/disk-operations.ts:90-91`、`:109-112`。
- 触发：undo 已重新链接回 source 并移除 target，但 `undone` 状态尚未写入日志时退出。
- 原因：再次 undo 首先要求 target 存在。即使 source 已经是正确的恢复文件，也被当作恢复失败。
- 实际复现：撤销子进程在移除 target 后退出；source 已恢复、target 不存在，但重试报“目标文件已消失或被修改”。
- 修复：恢复状态机必须同时覆盖执行和撤销；验证 source 已恢复时可以安全补记进度，遇到外部改动仍停止且保留文件。
- 验收：撤销的每个文件操作和日志边界都可中断、重启、重试；不会因重复恢复而损坏文件，也不会永久卡在错误状态。

### R3 · P1：预览允许已有文件夹移动，执行却拒绝

- 位置：`01_源码/electron/filesystem.ts:175-245`；`01_源码/src/components/Dialogs.tsx:214-220`；`01_源码/electron/disk-operations.ts:139-146`。
- 触发：把已有真实文件夹拖入另一个已有文件夹。
- 实际复现：预览 `issues = 0`，满足确认按钮启用条件；apply 才提示不支持已有文件夹整体移动。已有文件夹重命名也受同一限制。
- 影响：用户能在画布完成一个不能应用的结果，直接违背产品的核心使用预期。
- 修复：预览与执行共用同一份能力判断和操作计划；下一版补齐本地文件夹移动、重命名及子项依赖处理。在功能补齐前，预览就标出不支持的操作并禁止确认。
- 验收：父目录移动与子文件再分类、嵌套目录移动、空文件夹重命名等均有明确结果；所有支持的画布结构改变都能执行并经真实目录核验，不允许静默跳过。

### R4 · P2：仅修改文件名大小写时，预览通过，Windows 执行报错

- 位置：`01_源码/electron/filesystem.ts:212-217`；`01_源码/electron/disk-operations.ts:224-226`。
- 触发：在 Windows 常规目录中将 `Example.txt` 改为 `example.txt`。
- 原因：预览认为不是与其他文件冲突；执行仍直接创建目标硬链接，因同一路径已存在而返回 EEXIST。
- 实际复现：预览无问题，执行报 EEXIST，原文件仍保留。
- 修复：实现带日志的独占中间名称处理，并核对大小写结果；完成前在预览明确标为不支持，避免让用户到最后才失败。
- 验收：只改大小写、普通重命名、同名冲突分别测试；失败不会覆盖文件，恢复后名称正确。

| 缺口                                 | 代码依据                                                                               | 产品化需要做的事                                                                           |

安全边界已有较好的基础：主进程限定授权目录与 IPC 来源；preload 暴露受限接口；目标存在时不覆盖；密钥使用系统加密；AI 的删除建议仅是标记。这些应保留并纳入回归。此次审查不是完整渗透测试，也没有验证真实第三方模型的质量。

## 界面审查结论

已有类型图标、文字预览、图片缩略图、文件夹展开和目标高亮，可继续利用。主要问题是“操作当前处于哪一步”不够显眼：待应用变化缺少固定入口；眼睛、展开、外部打开等小图标容易混淆；计划撤销和磁盘恢复需要更明显地区分；执行失败目前主要靠约 6.5 秒的提示承载。

界面改进清单和验收标准放在产品化规划中。新增图标优先使用当前 Lucide 系统与矢量样式，不为此引入图片生成或另一套图标框架。
