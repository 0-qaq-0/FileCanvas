# FileCanvas 0.4.1 可靠性改进记录

日期：2026-10-20。基线：Git `5c4b231`（0.4.0 加路线图文档）。范围：[成熟产品路线图](成熟产品路线图_2026-10-20.md) 的 P0-1、P0-2、P0-3。包版本号仍为 0.4.0，没有打包 EXE；版本号和 CHANGELOG 留到准备发布时一起更新（根目录 `CHANGELOG.md`、`README.md` 目前有未提交的改动，本轮没有触碰）。

## 改了什么

| 路线图项 | 改动                                                                                                                                                                                                                  | 位置                                                                                                                             |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| P0-1     | 预览基线、应用前复核、核验和恢复都只比较“这次计划涉及的路径”（源、目标、要新建/移除的目录，以及它们所在的目录列表），不再扫描整个根目录。去掉对整根 10000 项的限制。                                                  | `electron/operation-plan.ts` 新增 `scopedInventory`；`electron/disk-operations.ts` 的 `scopeOf`、`expected`、`verify`、`restore` |
| P0-2     | 硬链接共享同一个 inode，所以操作过程中用 `身份 + 大小 + 修改时间` 判断文件没变；完整读取内容只在预览（1 次）和最终核验（1 次）。日志新增 `size`、`modified` 字段；没有这两个字段的旧日志仍按内容哈希校验。            | `assertFile(..., deep)`、`FileMove`                                                                                              |
| P0-3     | 预览有可应用的计划时，在所选目录建一个检测文件并尝试硬链接；不支持就把原因写进每一项变更的问题列表，不生成确认计划。每个目录每次运行只检测一次；中断留下的检测文件在下次打开目录或检测时清理。                        | `DiskOperations.linkSupport`、`sweepProbes`                                                                                      |
| 附带     | 自动回滚成功后，错误提示改为“整理未完成，文件已自动恢复到原位置。原因：…”，不再让用户去找并不存在的恢复任务；恢复失败时提示保留了记录并可重试。预览窗口的“保留条目”改为只说明整理涉及的文件夹，因为不再读取其他位置。 | `disk-operations.ts` 的 `apply`、`undo`；`components/Dialogs.tsx`                                                                |

## 行为变化（需要知道）

- **无关文件不再被核对。** 根目录里与计划无关的文件新增、删除、编辑，都不会让应用被拒绝或回滚；引擎只对日志里的路径做硬链接、删除链接和删除空目录，不会触及其他文件。代价是：0.4.0 的核验在“引擎自身出错而误动了无关文件”时也能发现，0.4.1 不再有这层检查，这类缺陷靠回归测试（无关文件在应用和恢复后字节与位置不变）把关。
- **计划自己的路径仍然严格。** 源文件在预览后被改、目标位置被占用、目标目录里出现同名文件，仍然拒绝，且不覆盖。
- **预览到应用之间不再重读文件内容。** 同样大小、同样修改时间却内容不同的篡改，改为在最终核验时被发现并整体回滚（此前在应用前发现）。
- **检测会在所选目录里短暂创建并删除一个 `.filecanvas-probe-*` 文件**（毫秒级）。同步软件监视该目录时可能看到它。

## 测量对比

同一台机器、同一脚本（临时目录，已删除；脚本未纳入仓库）。单次运行，测试文件刚写入，读取大概率命中系统缓存。

| 场景                                       | 0.4.0                           | 0.4.1                 |
| ------------------------------------------ | ------------------------------- | --------------------- |
| 移动 1 个 2 GiB 文件：预览 / 应用 / 恢复   | 2.5 s / 21.0 s / 18.2 s         | 2.5 s / 2.4 s / 2.3 s |
| 对该文件的完整读取次数：预览 / 应用 / 恢复 | 1 / 9 / 8                       | 1 / 1 / 1             |
| 预览后其他目录出现无关文件，再应用         | 拒绝，要求重新预览              | 成功                  |
| 应用过程中根目录出现无关文件               | 整次回滚，提示“请查看恢复任务”  | 成功，该文件保持原样  |
| 根目录另有 10050 个无关条目                | 预览抛错“核对范围超过 10000 项” | 预览 6 ms，无问题     |

## 验证

- `tsc --noEmit` 通过；`vitest run` 8 个文件 68/68 通过（原 60 项加 `reliability.test.ts` 8 项）。
- 新增的 8 项在 0.4.0 引擎上有 7 项失败，只有“计划自己的路径变化仍被拒绝”这一条守护用例在新旧引擎上都通过，符合预期。
- 80 个中断恢复场景（`02_测试/交互测试/recovery-crash.mjs`）全部通过，应用 22 个、恢复 18 个文件系统写入边界与改动前一致。检测会产生链接写入，所以脚本在布防前先检测一次，检测本身的中断由 `reliability.test.ts` 的清理用例覆盖。同时修正了脚本里“非本目录调用被误算作第 0 步”的小问题。
- 用 0.4.0 引擎生成已应用的日志（含文件夹移动、新建目录、改大小写、事后新增无关文件），由 0.4.1 引擎恢复，目录树与原来完全一致，即升级后用户仍能恢复旧日志。该检查是一次性脚本，未纳入仓库。
- 桌面检查：`test:demo`（20 个示例文件）和 `test:expanded`（真实界面应用、恢复）通过。
- `test:e2e`、`test:ai` 两项旧检查失败。把本轮改动暂存、在 0.4.0 源码上重跑，同样失败，失败点分别是坐标比较（`electron.e2e.mjs` 第 160 行附近）和卡片尺寸断言（`canvas-ai.e2e.mjs` 第 82 行），与文件操作无关，本轮没有修复。

## 没有做的

- **P0-4 云盘占位文件**：本机没有 OneDrive，无法验证。预览仍会读取文件内容（1 次）。
- **回退引擎**：复制、核验、删除源，用于 exFAT、跨盘和网络路径，仍在路线图 P1-10。0.4.1 只做到“不支持就提前说明”。
- **没有在 exFAT/FAT32 上真机验证。** 本机所有盘都是 NTFS，测试通过 `fs.link` 注入失败来模拟。
- **哈希放入工作线程**：读取次数降到 2 次后收益变小，暂缓。
- 版本号、CHANGELOG、README 的使用范围描述（仍写着“核对根目录最多 10000 项”）、EXE 打包，待发布时一起更新。

## 回滚

本轮代码改动在单独的 Git 提交里，可用 `git revert <提交>` 整体撤回。0.4.0 与 0.4.1 的日志互相读得懂，但建议降级前先完成或恢复进行中的整理。
