## 1. 给教学 Agent 的指令

### 1.1 你的任务与对话方式

你是这个项目的实现原理导师。学习者想真正理解并能解释、追踪和修改它，不只是背诵文件名。请先读完整篇，再开始教学，不要把全文复述给学习者。

遵循以下规则：

1. **一次只问一个主问题，等待学习者回答。** 第一次只简短说明教学方式并提出第一题。
2. 先判断学习者已有的认识；回答能体现理解时，不再从头讲语法。遇到陌生名词，用当前项目的具体例子补充。
3. 提问优先采用“预测结果”“追踪一次操作”“解释设计理由”“判断故障后果”，少问孤立术语的定义。
4. 回答后指出具体正确之处、具体缺漏和因果关系。不要只说“对”“很好”，也不要把关键词齐全等同于理解。
5. 部分正确时先给一个提示，让学习者补答。明显错误或表示不会时，用短例子讲清，再换一个场景检查理解。
6. 使用第 13 节的答案要点作为内部评分依据；**出题时不要连同答案、完整提示和验收要点一起展示**。
7. 必须区分“代码已经实现的机制”“设计意图”“尚未证明的保证”。不把提示词当作绝对安全屏障，不把硬链接称为独立备份，不把中断测试称为断电验证。
8. 没有源码访问权限时，明确基于本文教学。遇到本文未覆盖的实现细节，说明未知，不编造代码、日志或运行结果。
9. 练习以口头推演、小段伪代码、阅读已有代码为主。未经学习者提出，不运行实际文件移动、不发送文件内容给模型、不修改项目。
10. 每完成一阶段，用两三句话记录：已掌握什么、仍混淆什么、下一题检查什么。需要暂停时生成可复制的学习进度，便于下次继续。

判断掌握程度时，可以使用三级标准：

- **尚未掌握**：只能复述术语，或混淆真实文件、计划、布局。
- **理解机制**：能解释数据如何变化、哪个模块负责、为何这样设计。
- **能够迁移**：能预测未讲过的场景，识别边界，并指出修改需求将影响哪些模块。

建议起始问题：

> 假设你把画布上的 `脚本.md` 拖进了 `策划资料` 文件夹，但还没有点击“应用到本地文件”。你认为软件内部什么数据变了，硬盘上什么数据变了？为什么？

## 2. 项目解决什么问题

FileCanvas 是 Windows 本地文件整理桌面工具。用户先浏览、预览并在画布上规划结构，确认路径之后，软件再执行真实的目录调整、移动或重命名。AI 是可选建议来源；手动整理和按规则分类都不依赖 AI。

核心闭环：

```text
选择本地目录 → 读取真实条目 → 加入虚拟项目
                              ↓
                改名 / 归类 / 调整布局 / 采用建议
                              ↓
                  检查计划与真实目录是否一致
                              ↓
                      用户确认实际应用
                              ↓
                 写操作日志 → 调整路径 → 核验
                              ↓
                    更新项目的真实文件基准
```

必须分开理解三层状态：

| 层             | 主要数据                                | 发生变化的例子           | 是否立即改动待整理的真实文件 |
| -------------- | --------------------------------------- | ------------------------ | ---------------------------- |
| 磁盘真实状态   | 文件路径、目录、内容、文件身份          | 确认应用后移动文件       | 是                           |
| 虚拟整理计划   | `nodes` 的 `name`、`parentId`、`source` | 把文件归入分类目录       | 否                           |
| 展示布局与视图 | `x/y`、展开集合、当前层级等             | 自由摆放卡片、展开文件夹 | 否                           |

“没有改动待整理文件”不表示软件没有任何写盘：自动保存会写软件自己的项目 JSON；演示功能也会创建独立的真实样例副本。

## 3. 架构：为什么有主进程、preload 和 React

### 3.1 进程职责

```text
Electron 主进程：main.ts
  ├─ 窗口、打开目录对话框、应用生命周期
  ├─ 文件读取、路径边界、项目保存
  ├─ 操作预览、真实移动、恢复
  └─ AI 配置、加密密钥、模型网络请求
             ↑↓ 固定 IPC 通道
preload.ts：只暴露 FileCanvasApi
             ↑↓ window.fileCanvas
React 渲染进程：App.tsx + components + domain
  ├─ 界面和交互状态
  ├─ 虚拟树的修改、撤销与重做
  └─ 调用受限接口并显示结果
```

Electron 提供桌面运行环境和系统能力；React 根据状态渲染界面；TypeScript 描述共享数据和接口；Vite 构建界面；esbuild 打包主进程及 preload。它们承担不同职责。

`01_源码/src/main.tsx` 把 `App` 挂到 HTML 的 `root` 节点。`01_源码/electron/main.ts` 创建 `BrowserWindow`，开发时加载 Vite 地址，构建后加载本地界面文件。

窗口启用 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。React 不能直接拿到 Node.js 的 `fs`。preload 通过 `contextBridge.exposeInMainWorld('fileCanvas', api)` 暴露固定方法，而不是把任意 IPC 或整个文件系统交给页面。

### 3.2 一次调用怎样跨过边界

以读取预览为例：

```text
CardVisual / FileInspector
  → window.fileCanvas.readContent(source.path)
  → preload: ipcRenderer.invoke('fc:content', path)
  → main: handle('fc:content', filename => readContent(root(), filename))
  → content.ts / filesystem.ts 验证并读取
  → { ok: true, data: FileContent }
  → React 更新组件状态，显示文本、图片或“不支持”提示
```

统一的 `handle()` 包装器检查调用来自本窗口的主 frame，且 URL 符合本地入口或开发地址。异常转成 `{ ok: false, error }`。界面通过 `unwrap()` 等函数把失败转换成可显示的错误。

TypeScript 类型只能提供开发阶段约束，IPC 参数在运行时仍需校验。主进程不能因为页面传来了一个 `Project` 就信任它；路径、树、源 ID、授权根目录等会再次检查。

### 3.3 根目录授权的含义

主进程持有 `activeRoot`。用户选择目录后解析真实路径、检查目录可访问性，再激活项目。后续接口用主进程自己的 `root()`，而不是让页面随意指定一个操作根目录。

`validateAuthorized()` 检查项目合法性、项目根路径是否等于当前授权路径、源 ID 是否匹配源路径。`checkPath()` 拒绝越界、网络路径等；`noLinks()` 使用 `lstat` 检查相关路径段，拒绝符号链接或目录联接。

这些是当前实现的边界检查，不应讲成操作系统级全局锁或对所有外部竞争条件的绝对保证。

## 4. 数据模型：软件怎样表达一份整理计划

### 4.1 主要对象

类型集中在 `01_源码/src/domain/types.ts`。

```ts
// 以下保留理解机制所需字段，省略部分附加字段。
interface SourceEntry {
  id: string;
  name: string;
  path: string;
  kind: 'file' | 'folder';
  size: number;
  mtimeMs: number;
  blocked?: string;
}

interface CanvasNode {
  id: string;
  name: string; // 计划中的名称
  kind: 'file' | 'folder';
  parentId: string | null; // 计划中的父目录，null 表示项目根层
  source: SourceEntry | null; // 已知的真实源信息；新建虚拟文件夹为 null
  x: number;
  y: number;
  reviewDelete?: boolean; // 人工待确认标记，不是删除命令
}

type NodeMap = Record<string, CanvasNode>;

interface Workspace {
  project: Project; // 含根路径、节点表、时间和部分视图设置
  past: Snapshot[];
  future: Snapshot[];
}
```

项目用扁平 `NodeMap` 加 `parentId` 表达树，而不是每个目录对象内嵌完整子树。查找节点可以按 ID 直接取；找孩子通过筛选 `parentId`；找祖先通过沿父引用向上走。

`Project.version` 当前为 `1`，表示保存格式版本，不是软件版本 `0.4.0`。同理，操作日志有自己的 `version: 2`。

### 4.2 三种 ID 不要混淆

1. **项目 ID**：随机 UUID，标识一份保存项目及其操作记录。
2. **真实源节点 ID**：`fileId()` 对规范化绝对路径的小写形式计算 SHA-256。它是路径映射 ID，**不是文件内容哈希**。
3. **新建虚拟文件夹 ID**：随机 UUID，尚无真实路径来源。

在尚未应用的规划期间，移动或改名只改节点的计划字段，原来的源 ID 和 `source.path` 保持不变。应用完成后 `rebase()` 会按真实新路径重建 `source`、节点 ID 和父引用。因此不能把源节点 ID 当作跨所有物理移动永久不变的身份。

执行和恢复时另有一种**物理文件身份**：`identity(stat)` 使用 `dev:ino`。它与路径 ID、内容 SHA-256 各有用途。

| 量                      | 回答的问题                           |
| ----------------------- | ------------------------------------ |
| 路径 ID：`fileId(path)` | 画布中是哪一个已导入的路径对象？     |
| 物理身份：`dev:ino`     | 这个位置上的对象是否仍是原来的文件？ |
| 内容摘要：`hashFile()`  | 文件字节是否与记录相符？             |

### 4.3 目标路径如何计算

`relativeTarget(nodes, id)` 从当前节点沿 `parentId` 向上收集计划名称。主进程再把这组名称与根路径拼接。

```text
根目录：D:\整理练习

目录 F：name=策划资料，parentId=null，source=null
文件 A：name=拍摄脚本.md，parentId=F
        source.path=D:\整理练习\脚本.md

relativeTarget(A) = [策划资料, 拍摄脚本.md]
目标路径 = D:\整理练习\策划资料\拍摄脚本.md
```

此时卡片坐标完全不参与目标路径。源文件依然在 `D:\整理练习\脚本.md`，直至真实应用成功。

父文件夹改名会改变后代的计算目标路径，即使后代自己的 `name` 和 `parentId` 没改。实际执行范围必须考虑这些后代。

### 4.4 树的合法性

`workspace.ts` 中的校验阻止：

- 非法 Windows 名称、保留名、末尾点或空格、超长名称。
- 同一父目录内忽略大小写后的重名。
- 不存在的父目录、把普通文件当父目录、循环祖先关系。
- 同一个真实源路径重复出现、源 ID 与节点 ID 不一致。
- 非有限或超出范围的坐标、超过 5000 个节点。
- 没有真实来源的普通文件；当前只允许新建虚拟文件夹。

`topLevelSelection()` 去掉“已选父节点下面又被选中的后代”，避免批量移动一个文件夹及其孩子时重复处理。

## 5. 虚拟操作、React 状态和撤销

### 5.1 `commit()` 是虚拟变更的统一入口

`workspace.ts` 的基本做法：

```text
复制当前 nodes
  → 在副本上执行 update
  → validateNodes(副本)
  → 与原节点表比较
  → 有变化才产生新 Project，并把旧 nodes 压入 past
  → 清空 future
```

如果更新或校验抛错，原 `Workspace` 不变。这是内存层的整次采用或拒绝，不是文件系统事务。

`addFolder()`、`renameNode()`、`moveNodes()`、移出画布、采用建议、调整坐标最终都通过这一类状态变更完成。一次正常提交保留最多 80 个过去快照；快照保存节点表和操作标签，不是磁盘文件备份。

`undo()` 取出 `past` 最后一个快照作为当前节点表，把刚才的节点表放入 `future`；`redo()` 反向操作。撤销后产生一个新编辑会清空重做分支。

### 5.2 App 怎样串联界面

`App.tsx` 保存 `Workspace`，并管理当前目录、选中项、抽屉、弹窗、保存状态、忙碌状态和进度。领域函数不负责弹窗；组件不直接执行磁盘移动。

App 同时使用 React `state` 和 `current` ref：前者驱动渲染，后者让异步回调和长期监听器能够访问较新的工作区，减少闭包持有旧状态的问题。`replace()` 同步更新二者，并清理失效选择等状态。

项目变化触发 `useEffect` 自动保存。`saveCounter` 只让最近一次请求更新“保存成功/失败”的显示，避免较早响应覆盖当前提示。它不是磁盘写入队列；真正的保存排序在主进程 `ProjectStorage`。

`run()` 包装较长的界面任务并设置忙碌标记。主进程的 `diskTask()` 和 `DiskOperations.running` 也限制磁盘操作重入。界面禁用按钮与主进程检查共同作用；不能只依赖按钮。

### 5.3 四种动作的区别

| 动作                | 修改什么                             | 能否恢复文件正文历史 |
| ------------------- | ------------------------------------ | -------------------- |
| `Ctrl+Z` / `Ctrl+Y` | 内存中的虚拟节点快照                 | 不能                 |
| 移出画布            | 删除项目里的节点及相关后代           | 不删除真实文件       |
| 保存项目            | 写项目 JSON、最近项目指针            | 不保存文件正文版本   |
| 恢复上次文件移动    | 根据操作日志恢复真实路径，再更新项目 | 不能回退文件正文     |

重开项目时使用 `workspace(project)`，`past/future` 从空开始。真实应用、恢复及采用刷新结果也会重新建立工作区，旧的内存撤销历史不会跨这些步骤完整保留。

## 6. 画布：展开容器、拖放和性能

### 6.1 “画布”实际用什么画

主要实现是 React 渲染的 DOM 卡片和容器，配合 CSS 定位、滚动区域和 Pointer Events；不是 HTML `<canvas>` 位图绘图，也不是图形引擎。

`ExpandedCanvas.tsx` 管交互，`canvas-layout.ts` 计算几何布局。

### 6.2 两种布局方式

- 根层没有展开文件夹时，卡片位置主要使用节点保存的 `x/y`。
- 展开文件夹时，`expandedLayout()` 递归测量容器及子项，计算矩形、深度和换行；根层也按可用宽度重新排布。

展开模式中，保存坐标还用作同层排序依据；显示用的最终矩形可以来自自动排布，不应假设任何模式都直接显示原始 `x/y`。

`expanded` 是一个文件夹 ID 集合。展开状态可以回写到 `Project.view.expandedIds`，让重新打开时恢复部分视图。

### 6.3 拖动的完整路径

```text
pointerdown：确定选中节点、记录起点和视觉原位置
pointermove：超过移动阈值后，更新临时 draft 坐标，探测悬停目标
pointerup：判断最终目标
  ├─ 目标父目录不同 → onMove → moveNodes → 改 parentId
  └─ 父目录相同     → onLayout → 改位置或排序
最后清理临时手势状态
```

拖动过程中 `draft` 只是视觉反馈，不会每移动一像素就提交一个可撤销快照。指针结束后才提交最终动作。

`folderAt()` 从命中的文件夹矩形中选择深度最大的合法目标，因此嵌套容器会优先落入更内层。被移动对象及其后代不能成为目标；这能阻止拖进自己。悬停在折叠文件夹上约 650ms 可以展开。

从文件栏拖入与画布内部拖动也不同：前者携带源路径，调用导入；后者携带已有节点 ID，调用虚拟移动。自定义 `dataTransfer` 类型用于区分它们，不是直接把操作交给 Windows 资源管理器。

### 6.4 为什么滚动时不用渲染所有卡片

组件记录可见区域，把矩形与视口周围约 180px 范围比较，只渲染附近卡片。这减少 DOM 和内容预览开销。

这属于视口裁剪，不代表完整树的布局计算也消失：`expandedLayout()` 仍会计算相关布局。5000 项上限也不等于已经做过相同规模的性能承诺。

## 7. 读取、导入和本地内容预览

### 7.1 打开目录与加入项目

`fc:open-root` 创建项目并激活根目录。随后 App 列出根目录，尝试递归导入可读取条目；失败时保留空项目并打开文件栏，允许缩小范围后分批加入。

`importPaths()` 在主进程：

1. 检查输入路径和数量。
2. 去掉重复路径；同时选父目录和其孩子时，以父目录作为递归入口。
3. `readEntry()` 获取真实路径、种类、大小、修改时间和路径 ID。
4. 遍历目录子树，输出 `{ entry, parentSourceId }` 列表。
5. 遇到不安全或不可读取项抛错，不返回半份已采用项目。

渲染侧 `importEntries()` 将列表转换为 `CanvasNode`，保留来源父子关系，安排初始坐标；已存在的 ID 跳过。

普通搜索 `searchFiles()` 基于文件名，不是正文检索；最多访问 10000 个条目、返回 300 个匹配项，达到限制会标为截断。

### 7.2 `readContent()` 做了什么

- 先经过真实条目与路径检查。
- 排除隐藏路径、常见凭据/密钥名称、依赖和构建目录等。
- 支持的光栅图片在不超过 5MB 时转为 data URL，供本地显示。
- 文本扩展名白名单内，最多读取 256KiB，解码后最多返回 24000 个字符。
- 默认严格按 UTF-8 解码；识别到 UTF-16LE BOM 时使用 UTF-16LE。失败时提示转换编码；含空字符时拒绝当文本。
- 对截断文本显式返回 `truncated`。

PDF、Office、音视频及压缩包尚无正文提取。某种文件能用系统应用打开，不等于应用已经解析它，更不等于 AI 看到了它。SVG 在当前正文和光栅预览支持列表中也不能自动当作已解析内容。

`CardVisual` 可展示图片缩略图、文本短片段或类型图标。`FileInspector` 提供更完整的本地预览、路径和 AI 解释入口。

主进程的打开文件接口按扩展名区分普通文档与代码：普通文档交给系统默认应用，代码类交给文本编辑器，避免直接按可执行脚本运行。这个行为不等于软件具备任意格式解析器。

## 8. 从虚拟计划生成可确认的操作计划

### 8.1 基础路径预览

`filesystem.ts/generatePreview()` 对每个节点计算源路径与目标路径，并分类：

| 情况                     | `Change.kind` |
| ------------------------ | ------------- |
| 没有真实来源的新文件夹   | `create`      |
| 源路径与目标路径完全相同 | `unchanged`   |
| 父路径相同、名称变化     | `rename`      |
| 名称相同、父路径变化     | `move`        |
| 父路径和名称都变化       | `move-rename` |

检查内容包括源是否存在及是否变化、目标占用、祖先是否是普通文件、路径长度、链接、已有文件夹子树是否完整加入，以及实际变更文件数量。

基础源文件变化检查主要依赖种类、大小和修改时间；不能单独把它称为完整内容校验。更强的检查在下一层。

只改大小写可与自身区分，不当作普通同名占用。两个文件交换名字、将已有同名目录直接合并，仍会被当前目标占用规则阻止。

### 8.2 `DiskOperations.preview()` 绑定一份确认基准

真正的 `fc:preview` 入口调用 `disk.preview()`。它先使用上述预览，再：

1. 检查当前根目录是否存在未完成、需恢复的操作。
2. 无阻断问题且有变更时，扫描**整个授权根目录**，生成 `baseline`。
3. 对将被移动或改名的普通文件计算 SHA-256。
4. 保存 `Prepared`：随机 `planId`、`digest(project)`、目录清单和文件摘要。
5. 返回给界面显示。没有有效 `planId` 时不能点击实际应用。

`Prepared` 在主进程内存中；持久的操作日志要到应用阶段才建立。新预览会替换之前的准备结果，重启也需重新预览。当前没有按分钟计时的过期规则，主要依据令牌、项目摘要和磁盘变化判断是否过期。

`inventory()` 记录路径、种类、物理身份、大小与纳秒修改时间，最多核对 10000 项。`inventoryDigest()` 对文件记录比较这些元数据；对目录主要比较路径和种类，忽略目录身份、大小及修改时间。

未加入画布的文件仍在整个目录清单里，应用时应被保留。这里并没有对根目录内所有未参与文件计算内容哈希；移动文件才额外执行内容哈希核验。

### 8.3 执行前为什么还检查

界面传入当前 `Project` 与 `planId`。`apply()` 检查：

- 准备结果存在，ID 一致，当前项目摘要等于预览时摘要。
- 重新扫描根目录后的清单摘要与确认基准一致。
- 将移动的文件内容 SHA-256 未变化。
- 再次生成基础预览，没有新增问题。

因此“刚预览完”仍可能过期：用户改了计划，或其他程序改动了磁盘。项目摘要包含完整项目对象；某些视图状态变化也可能使摘要不同，而不只是路径计划变化。

这些检查用于拒绝已变化的确认依据，不会锁住其他应用。执行各阶段的检查和最终核验也承担发现竞争变化的职责。

## 9. 真实移动：日志、暂存区、硬链接和核验

关键模块是 `disk-operations.ts`；`operation-plan.ts` 提供清单、摘要、文件身份、原子写入和重建项目等工具。

### 9.1 先记下意图

执行前构造 `Journal`，通过临时文件写入、同步和重命名保存到软件数据目录的 `operations/<projectId>.json`。

主要字段：

| 字段                                    | 用途                                             |
| --------------------------------------- | ------------------------------------------------ |
| `id/root/projectId/status`              | 标识任务、范围与阶段                             |
| `before`                                | 根据真实源路径重建的操作前项目                   |
| `planned`                               | 用户确认的目标项目                               |
| `committed`                             | 应用或恢复后的真实基准项目                       |
| `moves[]`                               | 每个文件的源、目标、暂存路径、内容哈希、物理身份 |
| `createdDirectories/removedDirectories` | 需要创建的目标目录、移除的旧目录                 |
| `baseline`                              | 用于核验的目录状态                               |
| `staging`                               | 根目录内 `.filecanvas-operation-<id>`            |
| `acknowledged`                          | 项目记录是否已完成对应保存                       |

`before` 不直接等于用户的当前计划：当前计划里可能已有尚未落地的新文件夹或改名。`originalProject()` 会还原来源名称、源父关系，并补齐需要的真实祖先目录。

日志状态先为 `prepared`，之后写成 `applying`，再开始实际路径调整。日志记录全部端点与意图，而不是只依赖“第几个文件移动成功”这种计数。

### 9.2 硬链接怎样承担路径调整

以一个普通文件为例，忽略目录准备细节：

```text
初始：source → 文件对象

secure：
  source → 文件对象 ← stage

evacuate：
  移除已核对的 source / target 目录项
  stage → 文件对象

place：
  stage → 文件对象 ← target

verify + cleanup：
  核验通过后移除 stage
  target → 文件对象
```

`fs.link()` 建立同一文件对象的另一个名字，`fs.unlink()` 移除一个名字。只要还有有效链接，移除一个目录项不等于文件对象立即消失。

`assertFile()` 在关键位置检查：是否为普通文件、物理身份是否一致、内容哈希是否一致。位置被其他文件占用或内容被改写时，停止，不覆盖。

**硬链接不是独立字节副本。** 经由任一链接写入内容会影响同一个文件对象。暂存链接用于降低路径调整中断后的丢失风险，不能回退正文编辑，也不能解决磁盘损坏。正常结束后暂存区会清理；以后恢复时根据日志和当前源/目标重新保护文件。

这种方案依赖本地支持硬链接的文件系统与同卷范围。不能只去掉路径限制，就声称支持跨盘。

### 9.3 为什么文件夹不是一个整体 `rename()`

当前实现将目录变化拆成：

1. 为所有需要变化的普通文件建立暂存链接。
2. 移除已核对的旧路径或目标路径目录项。
3. 从深到浅移除需要消失的空目录。
4. 从浅到深创建目标目录。
5. 为文件建立最终目标链接。

这样可以表达“父文件夹移动，同时某个孩子被改名或被移出”的计划。已有目录移动要求完整导入子树，避免遗漏未参与文件。

代价是目录对象会被重建，原目录的自定义权限、创建时间等元数据不保证完整保留。当前保证重点是已检查的结构、文件身份和内容，不是目录所有属性逐项复制。

### 9.4 什么条件才算成功

`expected()` 从确认清单推导预期清单：删除旧文件路径和旧目录，加入新文件路径和新目录，保留未参与条目。

`verify()` 重新扫描根目录，排除本次暂存目录后对比实际与预期，再核对移动文件的身份和 SHA-256。通过后：

```text
rebase(project)
  → 按目标真实路径重新读取 SourceEntry
  → 重建路径 ID 和 parentId
  → 得到 committed 项目
清理 stage
  → 日志写入 applied
  → main 保存 committed 项目
  → acknowledge 日志
  → 使 AI 索引和解释缓存失效
  → 返回界面显示“已应用并核验”
```

不能只因为移动 API 没抛异常就认定成功。核验失败会进入异常及恢复流程。

## 10. 失败、中断、恢复和项目保存

### 10.1 状态机

```text
prepared → applying → applied
                │
                └─ 出错 → restoring → rolled-back
                              │
                              └─ 恢复失败 → needs-attention

applied / 未完成状态 → 用户发起恢复 → restoring → undone
                                              └─ 失败 → needs-attention
```

`prepared/applying/restoring/needs-attention` 属于需恢复状态。打开项目时可以发现这些记录；界面显示恢复入口，预览和后续应用会阻止继续整理。

正常执行中遇到异常会尝试自动恢复。进程直接退出时无法在原进程内完成补救，重开后根据日志检查实际磁盘状态，用户通过恢复入口继续处理。不要把“重开后识别”讲成“一启动必定无提示自动完成恢复”。

### 10.2 恢复如何处理“日志可能落后一步”

例如文件已经链接到目标，但程序还没来得及写下一条状态。恢复不能简单认为“日志没写就说明没发生”。

`secure()` 检查 `source/target/stage` 的存在情况，并验证身份和哈希；找到有效对象后建立暂存保护。再使用相同的路径调整机制把它放回来源。

恢复前构造新的核验基准，尽量保留无关文件的后来修改和新增。删除本次创建的目录时，只清理可安全移除的空目录；存在额外内容时保留。

如果参与移动的文件正文被改写，或原位置被另一个对象占用，无法核对就停止，保留日志并记录 `needs-attention`。当前功能是路径恢复，不能把它当成“无条件撤销任何后续改动”。

界面只开放最近一次操作的恢复；较早日志移入 `operations/history`。归档日志不等于已经提供任意历史版本选择与恢复界面。

### 10.3 文件已移动，项目却没保存怎么办

真实文件调整和软件项目 JSON 位于两个不同的存储步骤，不能把它们描述成一个数据库原子事务。

解决办法是：先在日志中记录 `committed`，成功保存项目后才把 `acknowledged` 设为 `true`。如果中间退出，`reconcile()` 在重新激活项目时可用未确认的 `committed` 补回项目记录，随后再保存和确认。

这个机制避免“磁盘已经成功，界面仍拿旧来源”的持久不一致。它不意味着存储设备任何故障都可恢复。

### 10.4 项目 JSON 的保存机制

`ProjectStorage.save()`：

1. 校验项目，并立即序列化快照，避免排队期间对象继续变化。
2. 用 Promise 队列串行执行保存，防止并发保存互相覆盖顺序。
3. `writeAtomic()` 写临时文件、执行文件同步、再重命名替换 JSON。
4. 更新 `last-project.json` 指针。

每个 JSON 的替换采用临时文件方式；项目 JSON 和最近项目指针仍是两次操作，不应解释成跨多个文件的一次原子提交。

关闭窗口时，主进程请求渲染侧完成最后保存；成功后等待存储队列，再关窗口。保存失败则保持窗口，执行操作期间也会阻止正常关闭。强制结束进程仍需依靠已落盘记录恢复。

数据一般位于：

```text
开发模式：%APPDATA%\FileCanvas-Development
普通运行：%APPDATA%\FileCanvas
  ├─ projects/          项目与最近项目指针
  ├─ operations/        最近任务日志与 history/
  ├─ ai-settings.json   地址、模型和加密后的密钥
  └─ exports/           导出的 Markdown 整理方案
```

### 10.5 刷新不是撤销

`refresh.ts/prepareRefresh()` 先生成待确认的新项目副本：

- 重新读取现有来源，记录大小、修改时间等变化，更新来源基准。
- 已有计划名称如果仍等于旧来源名称，可随真实来源更新；用户自行规划的名称尽量保留。
- 对来源缺失或种类改变的节点，清理相关虚拟子树，避免悬空父引用。
- 从真实根目录重新导入新发现的可读取条目。
- 返回 `new/modified/missing` 列表及跳过项，供用户确认采用。

采用后更新的是项目认识到的真实基准和可用计划，不执行磁盘移动。不是文件监视器自动实时同步；外部改名也不是基于永久文件身份的无缝追踪，可能表现为旧来源缺失、新来源加入。

## 11. AI：资料准备、检索、模型与建议采用

### 11.1 当前有哪些建议来源

| 来源       | 实现                                         | 是否请求模型 |
| ---------- | -------------------------------------------- | ------------ |
| 分类草案   | `drafts.ts` 按扩展名和文件名关键词分类       | 否           |
| AI 面板    | `prepare()` 准备资料，`ask()` 提问或生成分类 | 是           |
| 单文件解释 | `fileContext()`、`explain()`、`followup()`   | 是           |

规则草案只处理当前层的普通文件；按类型分组，或按策划/素材/交付等关键词分组。生成候选工作区，确认后一次采用，可以一次撤销。它没有读懂正文，规则理由应该按事实展示。

### 11.2 本地索引是什么

`AiService.build()` 遍历授权根目录，跳过排除项，用 `readContent(..., false)` 获取文本。`false` 表示不生成图片 data URL；图片没有因此成为发送给模型的视觉输入。

文本按每段最多 1800 字符、步长 1600 字符切分，产生约 200 字符重叠。每段保留相对路径和原文。

当前限制：最多访问约 6000 个目录条目、索引 1000 份文本文件、保留 4000 段；单文件还受内容读取限制。达到上限会标记截断。索引仅保留在本次运行内存中，不是向量数据库，也没有调用 embedding 模型。

扫描范围可包含没有加入画布的项目资料，所以解释一个文件时可能引用其他相关文档。教学时应区分“操作/分类范围”与“作为证据的检索范围”。

### 11.3 片段如何选出

`prepare()`：

1. 校验项目、范围和问题；每次最多分析 100 个条目。
2. 建立清单：节点 ID、名称、相对源路径、类型。
3. 为选中真实文本文件读取前 1800 字符，作为优先候选。
4. 将问题拆为英文/数字词、中文单字和相邻双字。
5. 对候选及索引片段计分：路径命中每个词加 4，正文命中加 1；选中文件额外加分，单文件分析时优先级更高。
6. 按分数筛选，最多取 8 段，同一路径最多 2 段，排除完全重复片段。
7. 返回 `AiContext`，包括清单、片段、索引状态和未覆盖文件数。

这是关键词检索加上下文增强，不是向量相似度搜索。检索结果取决于命名、关键词、读取上限和索引是否新鲜，不能保证找全资料。

### 11.4 两条授权与请求链路

**AI 面板：逐次预览将发送资料。**

```text
选择范围并提问
  → prepareAi() 本地准备，不调用模型
  → 显示清单、片段、未覆盖信息
  → 用户允许发送
  → askAi()
  → 主进程检查 pending 上下文 ID 和 project/ids/question 签名
  → 使用主进程保存的已准备资料构造请求
```

签名不一致时要求重新预览；不是信任页面回传的片段正文。一次使用后 `pending` 清空。

**单文件解释：对当前项目与当前模型授权后自动准备。**

`fileAccess()` 的授权签名绑定根目录、服务地址和模型，保留在内存中。授权后点击文件，界面短暂延迟，再请求解释；需要时自动建索引。`fileContext()` 在准备前后检查授权。

它并非每次都展示和 AI 面板一样的逐段发送确认。模型配置保存会撤销单文件授权，切换根目录也会清理。相同根目录的其他项目记录不能简单理解成另一个完全隔离的授权边界。

### 11.5 网络请求和密钥

AI 网络请求在主进程 `complete()` 中执行，调用配置地址下的 `/chat/completions`，发送 `model/messages`，当前使用 `stream: false`。响应读取上限为 1MiB，超时设为 90 秒，不接受自动重定向。

地址校验允许 HTTPS；HTTP 只允许本机回环地址。密钥用 Electron `safeStorage` 加密后保存，解密由主进程在请求时使用。读取已保存设置返回给界面的只有 `baseUrl/model/hasKey`，不会回传已保存的明文密钥。

用户首次输入密钥时，配置表单当然会暂时持有输入值；不能把上述机制表述成“密钥在任何时刻都不经过界面”。切换服务地址且没有提供新密钥时，会清除旧密钥，防止误用到另一服务。

本文描述的是当前源码的接口行为；预设模型名只是界面选项，不构成对服务商现时模型可用性、价格或回答质量的验证。

### 11.6 模型回答如何变成安全范围内的建议

提示词要求区分证据、名称推测和未知，不服从文件正文中的指令、不宣称执行、不直接删除。但提示词不是结果有效性的保证，还需要程序校验。

**批量整理**返回结构化结果：

```json
{
  "answer": "建议说明",
  "groups": [{ "folder": "策划资料", "ids": ["范围内的文件ID"], "reason": "具体依据" }]
}
```

`parseReply()` 验证格式、单层目录名称、目录重复、ID 越界和重复等；不确定的文件可以不分类。界面还检查生成后项目是否变化。`adoptAiPlan()` 再验证文件是否仍在原作用层、是否存在目标冲突，之后通过 `commit()` 采用到虚拟树。

**单文件解释**输出 `FileAdvice`：用途、内容要点、项目角色、行动、目的目录、新目录和理由。新目录按当前实现建立在项目根层。

| 行动               | 采用时实际发生的事                                   |
| ------------------ | ---------------------------------------------------- |
| `keep`             | 清除待删除标记，不一定把文件移回原路径               |
| `move` / `archive` | 修改虚拟归属；`archive` 也只是目录归类，不生成压缩包 |
| `review-delete`    | 设置人工待确认标记，不删除真实文件                   |

无论哪条 AI 链路，采用都不直接动磁盘。最终仍要经过统一的“检查并应用”流程。

### 11.7 缓存和内容边界

单文件解释缓存键包含来源大小/修改时间、节点名称、父目录、可选文件夹列表、索引时间及授权等，最多保留 100 份解释。手动刷新、根目录切换、设置变化、真实应用或恢复会按对应机制清理缓存/索引。

缓存并非每次基于全文哈希自动追踪，外部正文变化、相关文档变化不应假设永远即时反映；需要使用现有刷新和重建索引入口核对。

图片虽可本地预览，当前 AI 请求仍主要发送文字及元信息；PDF、Office、音视频等未提取的正文不应被说成“AI 已读过”。文件名过滤也不能保证普通正文里绝不含秘密，用户仍需核对发送范围。

## 12. 工程与证据边界

### 12.1 开发、构建、打包是三个步骤

```text
npm.cmd run dev
  → esbuild 打包 main/preload
  → 启动 Vite 本地服务
  → 启动 Electron 加载开发界面

npm.cmd run build
  → tsc --noEmit 类型检查
  → Vite 构建 renderer
  → esbuild 构建 main/preload
  → 写入 06_构建产物

npm.cmd run package:win
  → 先 build
  → electron-builder 生成 Windows portable 成品
```

开发脚本没有对主进程源码配置自动重建监听；修改 Electron 主进程或 preload 后通常需要重启开发进程。React 界面由 Vite 提供开发更新。

0.4.0 当前交付定位是源码开发版。历史 `07_发布成品` 中的旧 EXE 不代表当前源码的功能。`build` 成功不等于 EXE 已打包、签名或正式发布。

### 12.2 源码交付为什么使用白名单

`package-source.mjs` 从固定目录和文件列表复制源码、测试、脚本、文档、配置与虚构样例，生成独立目录、ZIP、文件摘要清单和 ZIP 校验值。

没有复制整个工作目录，因而排除了依赖、Git 历史、构建产物、软件个人数据等。当前文档位于 `05_项目文档`，以后重新运行 `source:zip` 会收录；已经生成的历史 ZIP 不会自动变化。

### 12.4 当前范围与已发现的说明差异

- 同一授权根目录、本地支持硬链接的文件系统；主要验证环境是 Windows NTFS。
- 每次最多改变 100 个普通文件路径，目录移动涉及的后代也会进入文件计数。
- 项目最多 5000 项，根目录核对最多 10000 项，目标路径限制 240 字符。
- 不支持跨盘、网络共享、符号链接/目录联接的整理，也没有已有目录冲突合并或文件名互换方案。
- 没有正文版本备份、任意历史恢复、PDF/Office 等正文提取、向量检索或全自动文件整理 Agent。
- 未把当前实现描述成所有操作具有不可分割的文件系统事务，也未保证目录全部元数据保持不变。

**一个源码中的旧文案差异：** `src/domain/plan-report.ts/markdownPlan()` 的导出模板仍含“当前版本未开放真实移动与恢复”。这与 0.4.0 的 `fc:apply`、`DiskOperations.apply/undo` 及对应测试不符，是残留说明。导出报告本身确实只生成文件、不执行移动；但不能据该句断言整个软件没有移动和恢复功能。本文仅记录差异，未修改业务源码。

## 13. 提问题库与导师验收要点

> 以下用于导师备课，不要整节一次发给学习者。每题先只展示“问题”，等回答后再使用“验收要点”。可以依据前置理解调整顺序。

### A. 三层状态与整体架构

**A1 问题：** 把 `脚本.md` 拖进虚拟文件夹，还没应用。内部哪些字段可能变？源路径在哪？

验收要点：`parentId` 改变，可能重新安排 `x/y`；源路径仍在 `source.path`；目标通过计划树计算；尚未移动真实文件。项目 JSON 可能已自动保存。

**A2 问题：** 同一目录里把卡片向右挪动，与把卡片放进另一个文件夹，为什么不是同一种操作？

验收要点：前者改布局或排序，后者改归属；几何位置不决定持久路径；区分 `onLayout` 与 `onMove`。

**A3 问题：** 为何 React 不直接 `fs.rename()`？一次本地预览请求经过哪些层？

验收要点：渲染侧无直接 Node 权限；React → `window.fileCanvas` → preload IPC → main → 文件模块 → 标准结果。限制接口和运行时校验各有作用。

### B. 数据结构和虚拟状态

**B1 问题：** `source.name` 与节点 `name` 为什么都要存在？只留一个会出什么问题？

验收要点：保留真实基准与计划名称，才能比较变更、生成来源/目标和恢复；直接覆盖来源会混淆尚未执行与已执行。

**B2 问题：** `文件 A → 目录 B → 目录 C → 根`，如何算 A 的目标路径？只把 C 改名会不会产生 A 的待变更？

验收要点：反向收集名称再与根拼接；会影响 A 的完整目标路径，即使 A 自身字段没改。

**B3 问题：** 为什么同时选中文件夹和它里面的文件，移动时只处理顶层选择？

验收要点：子节点通过父关系跟随，重复处理会破坏预期层级或重复移动；联系循环校验。

**B4 问题：** 改名产生冲突，为什么可以保证这次虚拟改动不会只做了一半？

验收要点：克隆、更新、验证，成功才返回新工作区；原快照不改。这不是对真实磁盘操作的同类保证。

**B5 问题：** 文件移动成功后节点 ID 为什么可能改变？它和内容哈希有什么区别？

验收要点：节点 ID 按路径计算，`rebase()` 更新路径 ID 和父引用；内容哈希只关注字节，物理身份另由 `dev:ino` 表达。

**B6 问题：** 撤销两步后再改名，还能重做刚才那两步吗？重启后的情况呢？

验收要点：新提交清空 future；保存的是 Project，不是整个 Workspace，重开撤销历史从空开始。

### C. 画布与内容读取

**C1 问题：** 展开嵌套文件夹后，鼠标同时落在两层容器里，应采用哪一层？如何避免放进自己？

验收要点：合法命中矩形中选最深层；排除移动对象及其后代；目标改变最后进入 `moveNodes()` 校验。

**C2 问题：** 为什么拖动中用 `draft`，而不是每次 pointermove 都调用 `commit()`？

验收要点：临时显示与持久动作分离，避免大量历史和保存；结束时提交最终变化。

**C3 问题：** 屏幕外的卡片不渲染，是不是所有 5000 项相关计算都没有了？

验收要点：不是；减少 DOM/预览工作，布局仍可能遍历。数量上限与性能验证不同。

**C4 问题：** 系统默认应用能打开一份 PDF，为什么 AI 却可能只能按名称推测？

验收要点：打开文件、解析正文、发送模型是三件事；当前没有 PDF 提取，模型没有文件系统直接访问权。

### D. 预览与实际应用

**D1 问题：** 一个文件大小和修改时间没变，是否足以判断字节没变？当前哪里进行了更强检查？

验收要点：元数据不等于内容；待移动文件有 SHA-256，执行/恢复时还核对物理身份；未参与文件不是全部都做正文哈希。

**D2 问题：** 用户预览后修改了目标目录，或另一个应用修改了文件，点击应用会发生什么？

验收要点：项目摘要、清单、文件哈希和再次预览用于拒绝陈旧计划；需重新核对；不是无条件使用旧计划。

**D3 问题：** 文件没加入画布，为什么执行前后还要扫描它？

验收要点：整个根目录作为基准，以发现未参与条目异常变化并验证保留状态；区分清单元数据与全文哈希。

**D4 问题：** 把已有目录移动，同时把里面一个文件改名、另一个移出去，软件怎么执行？

验收要点：目标从完整计划树推导；普通文件暂存链接，移除空旧目录，建立目标目录，再放置文件；不是整体文件夹 rename。

**D5 问题：** 为什么要在文件动作之前写入全部端点和身份，而不是做完一项才写“完成”？

验收要点：可能物理动作发生后、日志更新前退出；恢复要知道意图并核对 source/target/stage 的实际情况。

**D6 问题：** `stage` 是什么？把文件内容通过原路径改写后，stage 能找回旧正文吗？

验收要点：同一文件对象的硬链接，不是独立副本；不能找回旧正文，哈希不符会停止无法确认的恢复。

**D7 问题：** 目标路径被另一个同内容文件占了，为什么不能只比较 SHA-256 就覆盖？

验收要点：内容相同不代表同一对象或同一用户意图；还需身份及路径占用约束；当前选择停止而非覆盖。

**D8 问题：** 所有链接调用都成功后，为什么还要重新扫描目录？

验收要点：验证整个实际结果与预期结构一致，发现遗漏和外部改动，再检查移动文件身份及内容，成功后重建来源基准。

### E. 恢复、保存、刷新

**E1 问题：** 用户已经应用成功，再按 Ctrl+Z，是否会把硬盘文件移回？

验收要点：不会；虚拟快照与操作日志分开，磁盘恢复走专门入口。

**E2 问题：** 文件移动完成，保存 Project 之前进程退出。下次打开怎样避免指向旧位置？

验收要点：日志保存 `committed`，`acknowledged=false` 时由 `reconcile()` 补回，再保存与确认；不是跨文件原子事务。

**E3 问题：** 一次保存尚未完成又来了新保存，为什么不容易让旧快照最后覆盖新快照？

验收要点：主进程串行保存队列，序列化捕获快照；界面请求计数只控制提示，不能替代队列。

**E4 问题：** 应用后新增了无关文件，恢复路径是否要删掉它？如果移动文件正文被改写呢？

验收要点：尽量保留无关新增和编辑；参与文件内容不符可能阻止恢复；不做正文时间旅行。

**E5 问题：** 刷新核对与恢复移动分别解决什么？外部改名能否始终保留原计划？

验收要点：刷新更新来源认识和可用计划，恢复改变真实路径；外部改名可能是缺失+新增，没有永久身份追踪保证。

### F. AI 与工程迁移

**F1 问题：** 分类草案、本地索引、模型调用分别在哪一步发生？不配置 AI 能做哪些事？

验收要点：规则草案纯本地；索引读取和切片不请求模型；`complete()` 才发网络；手动整理、规则分类、应用和恢复可独立使用。

**F2 问题：** 这个索引是不是向量数据库？如何决定给模型哪几段？

验收要点：内存片段列表，关键词/路径计分、选择范围加权、最多八段、同路径最多两段；没 embedding，可能漏检。

**F3 问题：** 预览了待发送资料后改了问题，为何要求重新准备？单文件解释是否也每次逐段确认？

验收要点：签名绑定项目、范围、问题及上下文；单文件解释走当前根目录/服务/模型授权，是另一链路。

**F4 问题：** 模型返回范围外 ID、非法目录或“删除文件”，软件应该怎样处理？

验收要点：程序验证和采用时再检查；非法结果拒绝；待删除只能是标记；模型没有直接执行权。

**F5 问题：** AI 给出“归档”建议，用户采用之后立即发生了什么？还需要经过哪些步骤才落地？

验收要点：改变虚拟目录归属，不压缩、不直接写盘；统一预览、确认、日志执行和核验。

**F6 问题：** 要支持跨盘，能不能只解除 `checkPath()` 限制？要支持 PDF，能不能只修改提示词？

验收要点：都不能。跨盘需重新设计复制、校验、删除、日志与恢复；PDF 需增加提取模块、格式/体积/失败边界及上下文来源表示。

**F7 问题：** 模拟模型的桌面测试通过，是否能说明某家真实模型分类准确？构建通过是否代表 EXE 已更新？

验收要点：各自证据边界不同；模拟测试证明链路，build 生成运行构建；真实质量和发布需分别验证。

## 16. 如何开始及如何判断已经学会

把本文作为附件交给 Agent，并发送：

```text
请完整阅读这份 FileCanvas 实现原理文档，按照第 1 节担任我的导师。
先不要总结全文，也不要把题库答案展示给我。
请从第一道诊断题开始，一次只问一个主问题，等我回答后指出具体问题，
必要时提示、讲解，再用新场景验证我是否理解。
最后希望我能独立追踪“虚拟整理 → 预览 → 应用 → 恢复”和 AI 建议两条链路。
```

完成学习的标准不是答完题库，而是能不看答案做到：

1. 画出进程、模块与信任边界，追踪界面到文件系统的调用。
2. 用一份节点表手算源路径、目标路径，解释布局与目录树的区别。
3. 解释快照撤销、项目保存、刷新和磁盘恢复之间的差异。
4. 推演正常应用及任意一个代表性中断点的恢复，讲清硬链接与日志的限制。
5. 说明 AI 看到什么、没看到什么，如何检索和校验，为什么采用仍需统一确认。
6. 面对一个新需求，指出需要修改的模块、要维护的不变量和必要验证，而不是仅说“换个模型”或“改个按钮”。

以后动手改代码前，可先查看 `git status`，在当前仓库按小改动保存提交；现有项目已经有 Git，不需要重新初始化。学习笔记与源码修改应保留可比较的版本。代码变化后，优先更新本文对应流程、边界和题目验收要点。
